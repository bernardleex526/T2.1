# FastLIO2 时间同步方案（部署前提，非代码能力）

> 适用范围：Orin NX 上的 fastlio2 部署（雷达 Airy，`/rslidar_points`；IMU `/imu/data`）。
> 结论先行：**本仓库的 lio_node 不含任何时间同步实现**，同步必须由硬件或节点外的手段完成；
> 本文件**不给出任何同步精度指标**，也**不给出任何厂商/工具的具体操作命令**——这些都属于目标
> 硬件上必须实测/向厂商确认的内容。

## 0. 本仓库的现状（源码事实，勿与上游 FAST-LIO 混淆）

- `lio_node.cpp::loadParameters()` 只读取扁平键；**不存在** `time_sync_en` /
  `time_offset_lidar_to_imu` 的消费者。上游 FAST-LIO（`laserMapping.cpp`）里的这两个键
  在本仓库的 YAML 中是**惰性键**，写进去不会生效（`config/lio_orin_nx.yaml` 因此不再写它们，
  仅在本文件与配置文件头部注释中作对照说明）。
- 代码**假定** LiDAR / IMU（/ 相机）处于同一硬件时钟域：既不校验也不纠正。错域的直接表现是
  乱序告警 + 缓冲清空（`lio_node.cpp` 的 `imuCB`/`lidarCB`：`timestamp < last` 即
  `swap()` 掉整个缓冲），清空后 `syncPackage` 会因缓冲为空反复 `return false` 直到新样本到达。
- 本仓库**没有**“软同步门限 / 时间回拨日志”的实现。若需要，必须作为新增实现立项，
  不能当作既有功能使用。

## 1. 雷达/IMU 时钟域（部署前提）

- **Airy / Odin1 不是 Livox 产品**，因此 Livox 驱动自带的同步选项（其 `comm.h` 中的
  `kTimestampTypeGptpOrPtp` 枚举是**驱动内部枚举**）不能假定适用于 Airy/Odin1。
- 是否存在硬件触发/授时接口、支持哪些授时方式、以及能达到什么精度，**一律以对应雷达与 IMU
  的厂商文档为准**，并须在目标机箱上实测（本仓库无任何实测数据，也不引用任何转述的精度数值）。
- 部署前提：让 LiDAR 与 IMU 进入**同一时间轴**（硬件授时或外部节点改写 `header.stamp`）。
  这是部署条件，不是本仓库的代码能力；板端必须记录实测的同步方式与误差，而不是照抄手册指标。

## 2. 若采用“节点外改写时间戳”（推荐先验证这一路径）

本仓库**没有**任何可填入时间偏移的配置位（见 §0）。可行做法二选一：

- **外部节点**：在发布前改写消息 `header.stamp`，使两条流进入同一时间轴（推荐先用此法验证，
  因为它不改动本仓库代码）。
- **新增实现**：在 `syncPackage` 之前对 LiDAR 或 IMU 时间戳整体加偏移（需立项 + 板端验证）。

估计偏移量的方法（通用描述，本仓库**不附带**任何工具，也不认证任何第三方工具/命令）：
录制一段静止数据，对某条已知激励下的 LiDAR/IMU 信号做互相关或手持标定，得到整段常量偏移；
具体工具由标定承担方提供并验证其适用性。

## 3. 逐点时间语义（换雷达时必须核实）

- `PointCloud2` 路径下 `curvature = 相对帧首毫秒偏移`，但零点是**首个经距离过滤后保留的点**
  （`utils.cpp` 的 `pcl2_to_PCL`），不一定等于消息帧头：抽稀、距离过滤、驱动字段布局都可能整体平移。
- Airy 的逐点时间字段名/量纲**未验证**：`lio_orin_nx.yaml` 中 `pcl2_time_field: ""`，
  即当前**不做扫描内去畸变**（`curvature = 0`）。四足高动态下会表现为点云“锯齿/分层”。
  实测确认字段后再填 `pcl2_time_field` / `pcl2_time_scale`。

### 3.1 用工具实测，不要猜字段名

```bash
python3 tools/rslidar_pcl2_probe.py --topic /rslidar_points --once
#   或对已录的包：  --bag <bag> --topic /rslidar_points --emit-yaml
```

该工具按**实测值域**判定，而不是按字段名：

- 逐点时间的跨度必须约等于一个扫描周期（Airy 10 Hz → 0.1 s）；
- 由“哪个 10 的幂次能把跨度折算到约一个扫描周期”决定 `pcl2_time_scale`；
- 字段类型必须是 `FLOAT32`/`FLOAT64`。`UINT32` 纳秒是真实存在但**本仓库读不了**的
  字段（`pcl2_to_PCL` 只接受浮点），此时工具以退出码 2 明确拒绝，而不是给出一个
  会让补偿静默失效的配置值。

### 3.2 一个必须知道的上游事实

速腾官方 ROS 2 SDK `rslidar_sdk` 的字段布局由编译期宏决定：

| 构建选项 | 发布字段 | 逐点时间 |
|:---|:---|:---|
| `POINT_TYPE=XYZI`（**SDK 默认**） | `x, y, z, intensity` | ❌ 没有 |
| `POINT_TYPE=XYZIRT` | `+ ring, timestamp` | ✅ `timestamp`，`FLOAT64` |

因此“Airy 没有逐点时间字段”是**很可能出现的真实答案**，而不是工具故障。若如此，
必须改 SDK 构建选项重新编译驱动；在 YAML 里写一个不存在的字段名与留空等价
（`find_offset` 找不到即退化为 `curvature = 0`），却会让配置看起来“已填”。

### 3.3 本节与时间同步的关系

逐点时间解决的是**扫描内**运动补偿（一次扫描 0.1 s 内的畸变）；
本文件 §1–§2 讨论的是 **LiDAR 与 IMU 之间的时钟域**（量级 ms–s）。
两者是不同的问题，**不能互相替代**：字段填对了，时钟域不同仍然会漂移；
反之亦然。`tools/odom_static_drift.py` 能区分二者——单步大跳变指向时钟域，
平滑漂移指向外参/量纲。
